# 架构讨论备忘：Redis 缓存 / 消息队列 / 站点熔断

> 日期：**2026-09-09**  
> 给谁看：架构评审（可直接拿去 rebattle）  
> 结论先行：**先熔断 + 单机限流，再 Redis 分层缓存，消息队列不要上交互路径。**  
> 落地状态：**P0 已实现**（`SiteCircuitBoard` + `CrawlSingleflight` + Playwright 舱壁 2 + 后台 canary 嗅探）。P1 Redis / P2 MQ 未做。

当前后端是单进程 Spring Boot：爬虫在 SSE / Agent Tool 调用栈里 **同步** 跑完，Playwright + OkHttp，HTTP 超时 20s，WebView 导航 25s，Agent 整轮 120s。会话黑板、爬虫结果缓冲都在内存。**没有 Redis、没有 MQ。** 熔断是进程内滑动窗口，用户请求从不进入 Half-Open。

下面三条中间件，**不是同一优先级，也不是都该现在上。**

---

## 总建议（给架构哥打的牌）

| 优先级 | 做什么 | 用什么 | 为什么 |
|--------|--------|--------|--------|
| **P0 立刻** | 按上游熔断 + 舱壁 + 探测 | **已落地** 进程内 `SiteCircuitBoard`（不用 Resilience4j：Half-Open 不走用户请求） | 超时站点会拖死整轮 SSE |
| **P0** | 同关键词单飞（singleflight） | **已落地** `CrawlSingleflight` | 热门番同时搜会把源站打穿，零运维 |
| **P1 有流量再上** | 资源缓存 | Redis | 只缓存「剧目目录」，播放 URL 短 TTL 或点击再取 |
| **P2 预留，不要提前交租** | 消息队列 | Redis Stream 即可，不必上 Kafka | 只做预热 / 嗅探 / 刷新直链，**不要**把用户 SSE 请求丢进队列 |
| **P3 多实例时** | 熔断状态共享 | Redis 计数 | 单机时 Resilience4j 本地滑动窗口就够 |

一句话：**中间件是用来保护源站和用户等待时间的，不是用来把同步爬虫「微服务化」的。**

---

## 1. 熔断 + 定期嗅探（最该先做）

### 痛点

一次检索会串行打：插件站点 → YHDM → SiliSili，再加 Playwright。  
某个源站 522/超时，当前实现是「这条失败再试下一条」，但 **每一次用户请求都会再撞同一堵墙**，把 20s×N 吃进 120s Agent 超时，前端空转。

这和「高并发」无关，3 个用户同时搜也会把源站和 Chromium 打满。

### 建议形态：按上游隔离，不要整站一键断电

熔断粒度必须是 **一个上游一个开关**：

```
plugin:DM84 | plugin:SiliSili | fallback:YHDM | fallback:SiliSili
host:www.silisili.link | host:www.iyinghua.io | pool:playwright
```

- 用户请求只走 **Closed / Half-open** 的上游。  
- Open 的上游 **跳过**，用其它线路凑 `resource_bundle`。  
- 全部 Open 才对用户说「站点暂时不稳定」，而不是再空等 120s。

失败判定与现有 `ResourceCrawlerService.userFacingMessage` 对齐即可：timeout / ConnectException / 502–504 / 521–524 / 429。  
**不要**把「搜了没这部番」（空结果）算失败，否则冷门关键词会误杀站点。

### 探测（嗅探）不要走用户路径

架构同学说的「暂时关闭超时爬虫并定期嗅探」是对的，但探测必须是 **后台定时任务**，不要绑在下一次用户搜索上。

建议：

| 项 | 值（起步） |
|----|------------|
| 打开熔断 | 1 分钟内 5 次超时或 5xx，或失败率 > 50% 且样本 ≥ 5 |
| Open 停留 | 2～5 分钟 |
| 嗅探间隔 | 30～60 秒，每个 Open 上游 **最多 1 个并发** |
| 嗅探内容 | 固定 canary：打搜索页或 `GET /`，不要真的去解 35 条签名 URL |
| Half-open | 嗅探成功 1～2 次再 Closed；失败立刻再 Open |
| Playwright | 单独舱壁：全局最多 1～2 个 Chromium 上下文，排队超时直接跳过 WebView 走 OkHttp |

库：**Resilience4j** CircuitBreaker + Bulkhead + TimeLimiter。和 Spring Boot 3 匹配，不引入 Redis。  
多实例以后再把失败计数放到 Redis；现在两台机器各自熔断，最坏是一台还在打已经挂的源，可接受。

### 和架构可能的分歧

- 「熔断了就整爬虫停」→ 反对。SiliSili 挂了 YHDM 还能出片，bundle 里少一条线路而已。  
- 「失败就重试 3 次」→ 反对。超时重试是事故放大器。重试预算最多 1 次，且只对幂等 GET、非 Open 状态。  
- 「嗅探用真用户词」→ 反对。会污染缓存、误伤风控。用固定健康检查 URL。

## 2. Redis 做资源缓存（该上，但要分层）

### 该缓存什么

`resource_bundle` 已经把「给 LLM 的摘要」和「给前端的地址」拆开了。缓存应该贴在 **爬虫出口**，而不是 LLM 上下文。

建议两级 key，**禁止一套 TTL 打天下**：

```
crawl:catalog:{site}:{normalized_title}     TTL 6～12h
  → 作品名、线路名、集数标题、source_page、解密参数
    （没有 X-Amz-Signature，没有 m3u8.php 一次性 token）

crawl:play:{site}:{normalized_title}:{rev}  TTL 8～15min
  → 完整 resource_bundle（含可播 URL）
```

用户搜「帮我找鬼灭」「鬼灭之刃」必须归一到同一个 `normalized_title`（黑板 / 作品名清洗已经在做，缓存 key 要用这个，不要用 raw message）。

### 为什么播放 URL 不能缓存很久

昨天那批 R2 直链带 `X-Amz-Expires=3600`，一小时废。Sili 的 `m3u8.php?hash` 也很可能绑会话。  
若 Redis 里存 24h 全量 URL，前端选集看起来很美，点进去全 403——比没有缓存更糟。

所以：

1. **现在（P1）**：短 TTL 缓存完整 bundle + 命中后直接 SSE 下发，LLM 仍只拿摘要。  
2. **紧接着**：加一个 **刷新播放地址** 接口（或 SSE 内 `play_refresh`），前端点集数若 403 再拉一次。目录走长缓存，URL 走短缓存或懒刷新。  
3. 热门番用 `SET NX` + 锁做 **单飞**：第一个请求打源站，其余等同一个 Future，避免缓存击穿。

### Redis 不该做什么

- 不当 ChatMemory / 会话黑板的唯一存储（那是对话状态，和资源缓存寿命不同）。  
- 不把签名 URL 当「永久资源 id」暴露给前端书签。  
- 不在缓存未命中时把 SSE 线程堵在 Redis 超时上：Redis 挂了必须 **降级直连爬虫**。

### 体量判断

日活几十～几百检索：进程内 Caffeine（catalog 12h、play 10min）就够，Redis 可以等第二台 API 再上。  
只有「多实例要共享命中」或「预热任务和 API 不在同一进程」时，Redis 才是刚需。

给架构的立场：**同意引入 Redis，但第一个 PR 先 Caffeine + 熔断；Redis 作为 P1，且必须 catalog/play 分 TTL。** 否则就是用中间件把过期直链分发给所有用户。

## 3. 消息队列做「高并发预留」（现在不要接到用户请求上）

### 反对：用户搜番 → 丢进 MQ → worker 爬 → 再写回 SSE

交互路径已经是：

```
浏览器 SSE  ←阻塞→  Agent Tool  ←阻塞→  同步爬虫
```

再插一层队列：

- 必须把 `conversation_id` / SSE emitter 和 jobId 对上，超时、取消、断线全要重做；  
- 用户多等一次出队延迟，体感更差；  
- 当前瓶颈是 **源站 QPS 和 Chromium**，不是 API 线程不够。MQ 解决不了源站 522。

这叫「为高并发买期货」，在 QPS 还没打满本机线程池之前，是额外故障面（积压、重复消费、死信、积压告警）。

### 赞成：队列只用在非交互三个场景

等熔断和缓存稳定之后，用 **Redis Stream**（已有 Redis 就别上 Kafka）做：

| 场景 | 说明 |
|------|------|
| 熔断嗅探 | 定时把 Open 上游的 canary 丢进 `probe` stream，worker 限速 1 QPS/源 |
| 热门预热 | 榜单 / 前一天 Top 作品，低峰打 `catalog` 缓存，不生成签名 URL |
| 直链刷新 | 用户点播 403 后，异步换票；或即将过期的 R2 批量续签 |

交互检索继续同步（外加熔断跳过坏源、singleflight、短缓存）。  
并发保护用 **舱壁**：每上游许可 2～4 个在途请求，超额的这次检索跳过该源，而不是进队列排队 30s。

若架构坚持「预留 MQ」：可以 **先定义 topic 和 job schema，代码里留 `CrawlJobPublisher` 空实现**，等真有预热/嗅探任务再接 Redis Stream。不要为了预留先部署一套 Rabbit/Kafka。

Kafka 的时机：多机房、每天十万级预热、要回放/审计。现在没有这些信号。

## 4. 推荐落地顺序（rebattle 用的路线图）

```
Phase A（本迭代后立刻，无新中间件）
  Resilience4j：per-site CircuitBreaker + Bulkhead + TimeLimiter
  同关键词 singleflight
  Playwright 全局并发 = 1～2
  后台 @Scheduled 嗅探 Open 上游

Phase B（出现重复搜索 / 第二实例）
  Caffeine → Redis：catalog 长 TTL，play 短 TTL
  前端点播 403 → play_refresh（可先内部接口）
  Redis 挂了降级爬虫

Phase C（真有预热或嗅探要横向扩）
  Redis Stream：probe / warmup / play-refresh
  用户 SSE 路径仍然不进队列
```

### 成功指标（用来结案，而不是「上了 Redis 就算完成」）

- 坏源 Open 后，用户检索 P95 从「接近 120s」降到「其余源的正常耗时」  
- 同一标题 10s 内连点，源站只打 1 次  
- 缓存命中的 bundle 点播成功率不显著低于实时爬取（过期 URL 问题被 TTL 或 refresh 接住）  
- 交互路径无 MQ 积压告警（因为根本不走队列）

---

## 5. 可直接抛给架构的三句话

1. **熔断是可靠性问题，缓存是成本问题，队列是异步边界问题**——先修超时源站拖死 SSE，再谈 Redis，最后才是 MQ。  
2. **Redis 可以上，但必须把「剧目目录」和「可播 URL」拆开 TTL**；签了名的 R2 缓存一天等于给前端发过期票。  
3. **高并发预留 = 舱壁 + 单飞 + 按站点熔断**，不是把爬虫请求塞进 Kafka。队列只服务于嗅探/预热/换票这些可以失败重试、用户不盯着看的活。
